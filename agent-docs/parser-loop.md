# Цикл парсера (`src/parser.py`)

## Запуск
`docker compose up` запускает только `python3 /app/src/parser.py`. Старт: список магазинов
читается из `data/shops/shops.json` **один раз** (новый магазин = рестарт процесса), затем
`warm_up_etsy_authorization` (по одному `ping()` на магазин, чтобы обновить протухшие токены
до первого запроса), затем бесконечный цикл: `etsy_api_parser()` → `sleep(60)`.
Исключение из цикла ловится, парсер спит 900 с и продолжает.

## Один цикл
`ThreadPoolExecutor(max_workers=5)`, по потоку на магазин (`process_single_shop`):
1. статус парсера в бэкенде → `PARSING` (`PUT /parser/`);
2. `get_all_orders_by_shop_id(limit=ORDERS_PER_REQUEST, offset=0)` — последние N receipts
   (Etsy сортирует по дате создания, новые первыми);
3. каждый receipt → `format_order_data` → `OrderData`; вся пачка одним
   `POST /parser/orders/upload/` (см. [order-payload.md](order-payload.md));
4. по выходным в 19:00–19:02 по времени сервера — `parse_per_month` (ниже);
5. статус → `OK_AND_WAIT` + `last_parsed`.

## Окно заказов — это ещё и механизм повторной отправки
Бэкенд уже существующие заказы не создаёт заново, а только обновляет статус. Поэтому каждую
минуту заново уезжают одни и те же последние `ORDERS_PER_REQUEST` заказов, и если пачка не
доехала (бэкенд лежал), она уедет следующим циклом, пока заказы не вышли из окна.
Сейчас `ORDERS_PER_REQUEST = 50` (~3–4 дня для крупных магазинов, 10–20 дней для мелких).
Не поднимай его сильно: это N заказов на магазин каждую минуту, бэкенд уже упирался в пул
соединений к БД. `ORDERS_PER_REQUEST_PER_MONTH` объявлен, но не используется
(`parse_per_month` жёстко берёт `limit=100`).

## Недельная догрузка `parse_per_month`
Сб/вс в 19:00–19:02 листает заказы страницами по 100 с `offset=0`, пока не встретит заказ
старше 30 дней. Так подтягиваются заказы, выпавшие из минутного окна, и обновляются статусы
за месяц. Известные шероховатости: условие остановки сравнивает только день и месяц; если у
мелкого магазина нет заказа с такой датой, цикл не остановится. Из-за минутного тика может
сработать до трёх раз за вечер.

## Статусы и ошибки
`constants/status.py`: `OK_AND_WAIT=0`, `PARSING=1`, `COOKIE_EXPIRED=2` (не используется),
`ETSY_API_ERROR=3`. Статус виден в CMS (страница парсеров) и его раз в 30 минут проверяет
Telegram-бот: при `ETSY_API_ERROR` пишет в группу и тегает разработчиков.
- `ShopError` — Etsy не ответил/ошибка авторизации → `ETSY_API_ERROR`.
- `BackendError` — 10 неудачных попыток отправить пачку → тоже `ETSY_API_ERROR`
  (название вводит в заблуждение, но так завязан бот), в лог `critical`.
- Любое другое исключение только логируется, статус может «зависнуть» в `PARSING`.
`api/order.py::upload_orders_data` возвращает `False` на не-200 и на сетевые ошибки
(есть `timeout=30`), попытки идут подряд без пауз.

## Логи
loguru, JSON-строки (`serialize=True`), файл из `LOG_FILE`, ротация 100 MB, `enqueue=True`
для потоков. Внимание: `get_etsy_api.py` пишет в лог access/refresh токены Etsy при
обновлении. Пример формата — `logs.json` в корне репо.

## Другие точки входа
- `src/parser_all.py` — полная перезаливка истории: листает все заказы магазина по 100 и шлёт
  с `is_full_data_updating=True` (бэкенд тогда обновляет и клиента/город/доставку у
  существующих заказов). Запускается вручную, один проход.
- `src/parser_debug.py` — старая отладочная копия, вместо отправки пишет `test_data.json`.
- `src/auth_code_endpoint.py` — мёртвый (импортирует несуществующий модуль); код OAuth
  сейчас копируют руками, см. [etsy-auth-and-shops.md](etsy-auth-and-shops.md).
- `constants/commands.py` (`PARSE_NOW`, `UPDATE_ETSY_COOKIE`) — команды от бэкенда парсеру
  нигде не читаются, фича не реализована.
